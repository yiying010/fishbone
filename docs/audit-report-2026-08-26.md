## 已完成修補

### 功能正確性

| 問題 | 修補結果 |
| --- | --- |
| Step 14 的 UI 原本只執行本機規則，後端既有的 AI API 沒有入口 | 前端先同步最新快照，再呼叫同源 `POST /api/rooms/:code/ai/review`；處理成功、過期回應與無法使用的情況。 |
| AI 停用或供應商暫時不可用時，規則結果可能被呈現為 AI | 改為明確加上「本機規則檢查」；真正 API 回覆才標為「AI 建議」。 |
| 方法說明的 `oninput` 只改本機記憶體 | `methodEditSoft()` 現在會保存、廣播並排程同步，且使既有方法分類／確認狀態失效。 |

### 資安

| 問題 | 風險 | 修補結果 |
| --- | --- | --- |
| 未受限的快照識別碼與色彩直接進入前端 HTML 屬性／inline handler | 同房成員可植入儲存型 XSS，讀取 session token 或代替受害者操作 | 伺服器在快照信任邊界驗證技術識別碼、投票 map key 與 `#RRGGBB` 色彩；同時限制快照巢狀深度。 |
| `TRUST_PROXY=true` 信任任意 XFF chain | 攻擊者可偽造來源 IP、繞過建立房間與 API 限流 | 應用預設為不信任 proxy；隨附 nginx 範例改為覆寫 XFF，而非保留使用者提供的 chain。 |
| 已存在的 memberId 可被重新 join 並換發 token | 同房成員可使受害者登出並冒用其身分 | 已發過 token 的 memberId 必須帶原 bearer token 才能換發 session；前端於分頁 session storage 保存 token，以支援安全重新整理與續期。快照投影所建立、尚未發過 token 的成員列視為未被認領，第一個提出的瀏覽器可取得該身分，否則會把名列快照中但尚未加入的同學鎖在門外。 |
| 公開健康檢查回傳資料庫原始錯誤 | 洩露內部連線或 schema 細節 | 對外只回傳通用 unhealthy 狀態；完整錯誤僅留在伺服器日誌。 |
| 無效 JSON 走進通用 500 handler | 客戶端錯誤被誤視為服務異常並放大錯誤日誌 | Fastify 的 4xx parser／content-type 錯誤改為安全的 `bad_request` 回覆。 |

### SoC／品質

| 問題 | 修補結果 |
| --- | --- |
| 輸入事件兼具領域狀態、持久化與同步需求，但實作不完整 | 將方法說明修改收斂為明確命令：更新資料、失效下游分類、保存與排程推送；不在輸入時重繪。 |

新增／強化的驗證包含：

- AI 方法審查會使用已驗證的同源 API、帶 bearer token、帶 revision，並會捨棄 stale 回覆。
- AI 不可用時的本機規則標示。
- memberId 續用必須帶分頁保存的 bearer token；被拒絕的接管不會使原持有者的 token 失效。
- 尚未發過 token 的投影成員列仍可被本人認領，認領後即受同樣保護。
- 不安全識別碼、色彩屬性與過深巢狀快照會被拒絕。
- 同一個欄位名稱同時承載識別碼陣列與物件陣列（`causes`）時，兩種形狀都被正確檢查。
- 方法說明的 soft edit 會保存、同步、失效下游分類且不觸發重繪。

識別碼驗證與 session 擁有權檢查都以反向對照確認過：移除檢查後，對應測試會失敗，而非仍然通過。

## 尚待排程的改善

以下項目在審查中確認，屬於較大的協作協定或架構工作，未在本次小範圍修補中直接改動：

1. **協作資料完整性**：目前持有效 room session 的成員仍可提交整份 snapshot，伺服器尚未在 card、proposal、vote 層級強制「僅能修改自己的資料」。若匯出資料將用於研究或稽核，建議改為 server-authoritative 的 card／vote 命令 API，並讓作者欄位不可變。
2. **資源上限**：長輪詢尚無每個 token／房間的併發上限；AI 目前欠缺房間總額度限制。建議加入 per-member/per-room concurrency 與 budget。
3. **同源本機資料隱私**：完整活動快照仍儲存在 `localStorage`，同一 origin 的其他應用程式亦可讀取。最有效的措施是使用獨立 hostname；若無法，應移除完整快照的永久本機保存並設計明確清除策略。
4. **前端合併邏輯的 SoC**：前端資產已依責任拆分為有序載入的多個檔案，但 `mergeRoom` 仍以多層 wrapper 組成，`render()` 也同時承擔畫面、持久化與網路推送。建議在既有拆分之上再抽出 pure merge／command 模組，讓 render 成為純畫面更新。
5. **測試分層**：加入房間、身分擁有權與 Step 14 的 AI 檢查已由 `server/test/frontend-behavior.test.mjs` 實際執行出貨的前端 script 驗證，不再只靠 regex 斷言；其餘步驟仍是靜態文字比對，應逐步抽出純函式與 reducer，改用表格化行為測試。專案目前沒有 CI，所有驗證都仰賴開發者本機執行；應建立 CI 並提供 PostgreSQL service，讓需要資料庫的測試不會被長期略過。

## 建議後續順序

1. 為 snapshot 寫入改採卡片／投票層級的 server-authoritative 命令，先保護作者與投票者身分。
2. 加入長輪詢併發限制、每房 AI 總額度與寫入頻率限制。
3. 將魚骨洞天部署到獨立 origin，或移除敏感快照的永久 localStorage 保存。
4. 整併 `mergeRoom` 與 `render()` 的責任，並建立跨前後端快照契約測試。
